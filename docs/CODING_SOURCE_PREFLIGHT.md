# Coding verification fast path and the 35x target

A 3,400% throughput increase means 35 times the baseline throughput. This change does **not** establish that result for SARA's coding. The prior 35.47x correct-completion throughput was a simulation requiring 99.9% applicable repair reuse and 0.1-second checks, not measured production capability.

## Implemented changes

The Genome Lab verifier calls the same bounded TypeScript source guard before loading the semantic compiler graph or creating a candidate workspace. Disallowed source is rejected with an enumerated diagnosis and a source-only location. The builder independently repeats its guard. Protected-test source-policy errors expose neither their path, location, literals nor rejection reason. Existing critical-capability signals remain critical.

For eligible code, the real Genome Lab builder now supplies the structured compiler result. This removes a duplicate virtual TypeScript Program that previously repeated the same candidate's semantic work before the builder compiled it again. Every eligible verification still creates one fresh semantic compiler Program, performs the existing isolated behavioral execution, and hashes its artifacts. Each later controller/final verification repeats those checks afresh. No acceptance test, compiler option, permission boundary, or independent final verification has been removed. There is no cached PASS or mutable compiler-AST reuse.

Compiler errors retain typed codes and stable source locations. Compiler and infrastructure failures do not falsely claim that behavioral tests ran. Raw compiler messages, private child-process errors and temporary workspace paths are not placed in repair feedback. The existing live-task wrapper continues to redact protected-test compiler locations. The verifier snapshots the admitted candidate across asynchronous work. The Luna adapter no longer labels a failed policy or integrity check as previously passing.

An early rejection's 0.2 score means only the artifact-integrity stage passed. It is not a percentage of correct acceptance tests. Type checking and behavior are not recorded as performed on that path.

## Executed offline evidence

Node v22.16.0 and locked TypeScript 5.9.3 were used. The control implementation was main revision `4c722994a623fde631f93cce4de02be2c1f65096`.

Eighteen alternating-order old/new pairs used the existing known-correct verifier fixture and the unchanged broken scheduling task: nine positive controls and nine negative controls. All outcomes and candidate artifact identities matched. Both methods passed the correct fixture and failed the broken task through actual fresh compilation and isolated behavioral execution. The nine positive-control verifications totaled **7,450.199 ms before versus 3,822.071 ms after**, a **1.949x verification-component ratio** (48.70% less elapsed verification time). The first cold sample is included. Excluding it as a sensitivity check gives 1.821x, not a different primary result. These are repeated checks of an existing fixture, not nine newly solved coding tasks or a general coding-speed measurement. The fixture was not generated by a model in this experiment.

The six original proposals from consumed grant `33d94c9a-0de6-41d9-a843-fe9880994242` were checked unchanged in three rounds, alternating old/new verification order. All 18 pairs rejected the same proposals and retained identical candidate artifact identities. Total rejection-verification time was **6,820.198 ms before versus 14.060 ms after** (485.09x for this **rejection component only**). Every sample, including cold loading, was retained. These post-run diagnostics do not change the original failed live trial or become successful tasks.

The complete local `npm run verify` passed: 658 main tests, zero failures, followed by type checking and all existing proof commands. Added regression coverage was observed failing on the old implementation before passing on the new one. Tests cover premature compiler creation, exactly one fresh compiler per eligible verification, syntax/type/policy classifications, protected-test secrecy, wrong behavior, infrastructure failure, critical capabilities, mutation across awaits and model-facing feedback. GitHub CI and CodeQL remain required before merge; a local pass is not production qualification.

## What is unchanged

The task, hidden acceptance files, model, sampling settings, cycle limits, spending grants, original receipts, and historical unresolved $0.15 hold are unchanged. No provider request was made. Infrastructure/tool billing has not been reconciled. The repair-memory implementation remains a proof prototype; this patch does not claim it is deployed or able to reuse 99.9% of actual jobs.

## Remaining proof for 35x

A separately authorized matched live comparison must measure successful completions per total elapsed time, including new generation, failed attempts, verification, learning and memory misses. It must separately report novel work and exact-repeat work, and compare against an ordinary system with equivalent standard optimizations. These component ratios cannot be multiplied by earlier unrelated live ratios. A faster rejected proposal does not satisfy the target. A source merge also does not establish that Railway is running that revision.

Run the full regression suite with `npm run verify`. The focused subset is:
