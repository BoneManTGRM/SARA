# Full-kernel live qualification after acceptance/dispatch hardening

Owner continuation, SARA only. This work incorporates the previously local
kernel acceptance candidate, preserving workers OFF by default. The earlier
worker/default measurements did not establish an end-to-end speed gain; none is
inferred from their component timings. Adds stop/resume invalidation from initial
job admission, including generation, not only the subsequent verification stage.

## New protocol

A new one-use grant, 17430b72-1b04-4b9f-8f1c-e75b8b5f4235, caps the entire
three-arm trial at $0.15 and each arm at $0.05. All historical grants remain
held/consumed and their original code/pins/evidence remain unchanged. Activation
and an exact runtime/launcher SHA-bound short-lived permit are required. One
benchmark POST maximum; after uncertainty only evidence GETs. Existing false
source-pin expectations are retired explicitly, not changed to authorize replay.

The benchmark exercises the ACTUAL createSaraServer owner endpoint and
SaraKernel in isolated persistent lab directories on the existing operator.
Synthetic lab funding is solely local job admission; it is not production revenue
or authority to spend. An independent existing suite budget reserves up to $0.0156
before each provider generation. No customer jobs or generated-code promotion.

Three arms each run four jobs on the historical protected freeWindows task:
regenerate uses new proposal memory per job; ordinary memory retains its own
repairs with legacy loop checking; optimized memory retains its own repairs with
native loop checking. All use identical Luna/medium/8000-output settings, the
actual hardened server/controller, fresh legacy finals and independent kernel
verification. Each memory arm begins empty and learns its OWN real generated
solution. Responses in ordinary CI are explicitly scripted; live CLI forbids a
supplied fetch implementation. This is not an all-features-off ablation.

Provider deadlines are 45 seconds in ALL arms, declared before execution (the
historical failed trial used 30). No artificial inference delay or unconditional
retry. The whole suite refuses new dispatch after 400 seconds; the subprocess is
bounded to 600 seconds. Any failed job closes the trial; remaining jobs are
explicitly unrun, and no complete-job speed ratio is published for an incomplete
suite. An uncertain call remains counted from the actual dispatch journal even
when the repair-summary callback never completed. Responses are NOT invoices.

## Timing and evidence

Primary job time includes isolated job authorization/setup plus loopback HTTP
self-build submission through response body. The return follows all required
kernel acceptance event writes. HTTP-only and kernel stage timings are separate;
setup of the three lab kernels and shared native checker is separately reported.
Evidence export/auditing is excluded from primary latency and measured as an
additional boundary. No complete-customer/public-network lifecycle claim.

Every successful output must have a distinct kernel attestation, SHADOW mutation,
protected test bytes unchanged, current artifact hash, mandatory final receipt,
and matching persisted job events. Exact final source snapshots are exported for
credential-free audit. Only predetermined job/trace JSON paths are exported; never
arbitrary state, lab owner tokens, provider keys or production data. 128 files,
1MiB per file and 4MiB total existing export limits remain unchanged.

Pooled warm, learning-inclusive, ordinary-memory control, each individual repeat,
all failed/unrun jobs, request counts and uncertain reservations are mandatory.
35x remains a target, NOT a release criterion satisfied by a maximum outlier.
The historical 20.89x component result cannot be directly relabeled as this new
full-kernel measurement or multiplied by any local storage/compiler ratio.
