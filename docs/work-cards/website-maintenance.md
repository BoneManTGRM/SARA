# Website maintenance — initial CANARY candidate

Owner request: a durable unattended website-maintenance workflow, starting with the Óptica Montecristo gift site. Existing budget and account authority remain unchanged.

Acceptance criteria:
- Use the kernel's existing hash-chained event store for job state; no secondary ledger.
- Authenticated owner submits an exact, zero-cost gift change. Commercial intake remains blocked until service-bound payment and contract support exists.
- Only literal text changes in explicitly named content slots; no scripts, medical claims generated by a model, credentials, forms, or arbitrary shell commands.
- Exact base digest, unique request identity, deterministic candidate, independent verification, immutable artifact, and audit receipt.
- Background processing without an open browser; restart-safe state transitions and one job at a time.
- Persist deployment intent before dispatch. Reconcile uncertain outcomes by stable job identity; never blindly repeat a publish or notification.
- Freeze external work when emergency stop is active; never claim a delivery without a provider receipt and matching deployed-content digest.
- Provider configuration is trusted host configuration only. Missing publishing/delivery credentials produces an explicit blocked state, not successful fulfillment.
- Test real filesystem artifact production and restart behavior, with fake remote providers explicitly identified as test fixtures. A fake provider does not prove production delivery.

Production gate: This candidate does not itself approve a deployment, change protected secrets, establish commercial terms, activate a standing mandate, or collect payment. Live site delivery requires a target-bound owner approval and persistent provider connection. The gift is not revenue.

## Implemented candidate boundary

The HTTP owner routes are GET /api/website-maintenance/readiness and GET/POST /api/website-maintenance/jobs. POST accepts a request and approvedRequestDigest; the digest is SHA-256 of canonical validated request JSON. A missing digest returns the review digest without submitting work. The existing owner authentication boundary applies. Readiness deliberately reports disconnected and commercial intake disabled.

The runtime starts an inexpensive scheduler in the existing process. It has no configured provider. It cannot publish a website, send email, collect payment, or make model calls. Only a trusted project-specific provider can supply publishing, reconciliation, delivery, and rollback. Implementing that real adapter is outstanding; an interface is not a working account connection.

Candidate jobs produce source/candidate artifacts in the existing persistent state directory and append snapshots to the kernel audit. Publication mismatch enters rollback intent; restoration must match the original digest. Lost publication, notification, and rollback replies reconcile using provider-held stable keys. Failed calls use durable exponential backoff, permit other jobs to proceed, and after five failures retain a blocked review obligation. No paid ledger entry is recorded for a gift.

Provider activation requirements:
- One explicit project, source revision, destination and notification recipient, bound through trusted host configuration.
- Atomic publish compare-and-swap, stable idempotency keys, and independently retrievable published content.
- Rollback compare-and-swap against the failed deployment, preserving any newer changes.
- Notification reconciliation capable of resolving a lost response without blindly resending.
- Durable account access owned by SARA, not temporary ChatGPT connector credentials.
- Owner-approved content markers in the actual Montecristo site and one exact approved change.
- Target-bound production CANARY approval after review and required gates pass.

Outstanding commercial work: maintenance-specific service terms and mandate, payment-to-order binding, paid cost reservation/settlement through the existing ledger, supported recurring entitlements and intake, and customer-facing purchase/delivery integration. Existing repository-report payments cannot authorize this different service.

Live acceptance evidence must include the real job ID, source and candidate digests, publish receipt and independent live retrieval, delivery receipt, and cost record. It must finish with ChatGPT closed. Fixture tests below do not satisfy that acceptance criterion.
